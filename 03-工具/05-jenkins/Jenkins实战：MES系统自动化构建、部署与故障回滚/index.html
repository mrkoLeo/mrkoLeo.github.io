Jenkins 实战：MES 系统自动化构建、部署与故障回滚

发表于 2026-09-26 分类于 03-工具 ， 05-jenkins 阅读次数： 本文字数： 6.4k 阅读时长 ≈ 23 分钟

本文结合制造企业 MES 系统实际部署场景，介绍基于 Jenkins Pipeline 的自动化构建与发布实践。

通过整合 Gitea、Maven、Node.js、npm 与 Tomcat，实现前后端并行构建、依赖缓存、环境配置隔离、定时部署、生产双节点顺序发布、应用健康检查及失败回滚，减少人工操作，提高软件交付的标准化程度与可追踪性。

同时分析现有方案在健康检查和双节点整体回滚方面的局限，为后续持续交付体系建设提供参考。

一、项目背景

1.1 项目建设背景

随着制造企业数字化建设不断深入，MES 系统已成为生产业务的重要支撑系统。随着系统功能持续迭代，开发人员需要频繁进行代码更新、前后端构建、发布包制作及服务器部署。

传统的软件发布流程通常涉及多个环节，包括 Git 代码拉取、前端依赖安装、Vue 项目打包、Java 后端编译、前后端文件合并、环境配置替换、发布包上传以及 Tomcat 重启等。

这些操作如果主要依赖人工执行，不仅步骤较多，而且容易受到操作习惯、环境差异和人为疏忽的影响。

因此，本项目以 Jenkins 为自动化执行平台，结合内部 Gitea 代码仓库、Maven、Node.js、npm 和 Linux 服务器，建设 MES 系统自动化构建与部署流程。

1.2 项目建设目标

本项目主要围绕以下目标开展建设：

  1. 自动化构建： 自动拉取前后端代码，分别执行 Vue 前端构建和 Java 后端编译。
  2. 统一发布流程： 将前后端合并、环境配置覆盖、压缩打包和文件上传纳入统一流水线。
  3. 多环境支持： 支持测试环境、单节点生产环境以及生产双节点部署。
  4. 定时发布： 支持指定部署时间，在构建完成后等待至计划时间再执行部署。
  5. 发布安全控制： 部署前检查环境、文件、Java 和 Tomcat 配置，部署后执行健康检查。
  6. 故障恢复： 部署失败时自动尝试恢复历史版本，并对回滚后的系统进行健康检查。
  7. 过程可追踪： 通过 Jenkins 控制台日志、构建结果和阶段耗时记录，便于定位问题和复盘。

二、遇到的问题

2.1 人工构建与发布步骤繁琐

MES 系统由 Java 后端和 Vue 前端组成，两部分需要分别构建，最终还需要合并为可部署的应用目录。

完整流程涉及代码检出、npm 依赖安装、前端编译、Maven 打包、WAR 解压、前端文件复制、环境配置覆盖以及 ZIP 发布包生成。

如果每次发布都需要人工逐项执行，操作流程较长，容易出现遗漏步骤、文件覆盖错误或者发布包内容不一致等问题。

2.2 前后端构建耗时较长

前端项目依赖较多，每次重新安装 npm 依赖都会产生额外耗时。

同时，前端和后端如果采用串行构建，整体等待时间还会进一步增加。

因此，需要在保证依赖一致性的基础上，优化依赖安装流程，并尽可能利用前后端之间相互独立的特点执行并行构建。

2.3 多环境配置容易混淆

MES 系统需要部署至不同环境，各环境可能使用不同的数据库连接、应用参数、日志配置和其他运行配置。

如果直接使用同一个发布包部署所有环境，就可能出现测试配置进入生产环境的问题。

因此，需要建立明确的环境配置目录映射，并在发布包生成阶段完成配置覆盖，确保不同环境使用各自的配置文件。

2.4 生产双节点发布存在风险

生产环境包含 172.16.xx.102 和 172.16.xx.101 两个节点。

如果两个节点同时部署，一旦出现构建包异常、应用启动失败或配置错误，可能导致两个节点同时受到影响。

因此，需要控制部署顺序，先部署 102 节点，待健康检查通过后，再继续部署 101 节点。

2.5 Tomcat 启动成功不代表应用正常

Tomcat 进程启动成功，只能说明 Java 容器已经运行，并不一定代表 MES 应用已经能够正常提供服务。

例如：

  • Spring 应用启动失败。
  • 应用使用了错误的 Java 运行环境。
  • 前端入口文件无法正常访问。
  • 登录接口出现 404。
  • 应用启动过程中出现 Bean 注册冲突。

因此，部署完成后需要进一步验证端口、Java 路径、HTTP 响应和关键日志，而不能仅依赖 Tomcat 进程状态判断部署结果。

2.6 部署失败后的恢复操作复杂

如果新版本部署后无法正常运行，需要及时恢复旧版本。

人工恢复通常需要停止 Tomcat、处理新版本目录、恢复旧版本文件、重新启动服务并检查应用状态。

这一过程不仅耗时，而且在生产故障场景下容易因操作遗漏扩大影响。

因此，需要将备份、失败检测和回滚流程纳入自动化部署脚本。

三、问题分析

3.1 构建流程缺乏统一编排

前端、后端、配置覆盖和发布操作相互关联，但并非所有步骤都需要串行执行。

通过 Jenkins Pipeline，可以将整个交付过程拆分为多个阶段，并为每个阶段定义明确的输入、输出和失败条件。

其中，前端和后端可以并行构建；发布包生成则必须等待两部分构建完成。

3.2 依赖缓存需要兼顾速度与一致性

npm 依赖缓存虽然能够减少重复安装，但不能简单地认为缓存目录存在就可以直接使用。

如果项目依赖发生变化，继续使用旧的 node_modules 可能导致构建结果异常。

因此，本项目通过计算 package-lock.json 的 SHA256 值判断依赖锁文件是否变化：

  • 缓存目录存在且 SHA256 一致：恢复 node_modules 缓存。
  • 缓存不存在或 SHA256 不一致：执行 npm ci。
  • 安装完成后：更新缓存及对应的 SHA256 记录。

这种方式能够减少重复安装依赖的开销，同时以依赖锁文件作为缓存有效性的判断依据。

需要注意，锁文件哈希一致并不代表所有运行环境都完全一致；Node.js 版本、操作系统和原生依赖等因素仍需要保持兼容。

3.3 环境隔离应在发布包阶段完成

本项目采用环境配置目录映射方式，将环境差异控制在发布包生成阶段。

部署环境 配置目录 发布包
TEST-131 config/131 N131.mes200.zip
PROD-102 config/102 N102.mes200.zip
PROD-101 config/101 N101.mes200.zip
PROD-ALL 分别使用 102、101 配置 同时生成两个发布包

流水线先构建基础应用，再将对应环境目录中的文件复制至 WEB-INF/classes/，覆盖同名配置文件，最后分别生成发布包。

这样可以避免在部署过程中临时修改发布包内部配置，降低不同环境之间的配置混用风险。

3.4 部署安全需要多层检查

部署安全不能仅依赖 Jenkins 最终的 SUCCESS 或 FAILURE 状态。

本项目将检查分为多个层次：

  1. 部署前检查： 验证 Java、Tomcat 脚本、Webapps 目录和发布包。
  2. 停止服务检查： 尝试正常停止 Tomcat，必要时逐级强制终止进程。
  3. 备份检查： 保存当前版本，并保留原有备份的历史副本。
  4. 部署文件检查： 确认新版本包含必要的前端和后端配置文件。
  5. 启动检查： 检查 8080 端口监听、Tomcat PID 和实际 Java 路径。
  6. 应用检查： 检查前端入口 HTTP 状态、Spring 启动日志和登录接口。
  7. 失败恢复： 尝试恢复备份，并重新执行完整健康检查。

需要说明，当前 Jenkinsfile 中登录接口返回非 404 的情况仍可能被记录为 WARNING，而不是全部判定为部署失败。因此，健康检查仍有进一步细化的空间。

四、解决方案

4.1 整体技术架构

本项目采用 Jenkins 作为自动化交付中心，以 Gitea 存储代码，通过 Maven 和 npm 完成前后端构建，最终通过 SSH 和 SCP 将发布包传输至目标服务器。

主要技术组件如下：

组件 作用
Jenkins Pipeline 编排构建、打包、部署和回滚流程
Gitea 管理 Java 后端与 Vue 前端代码
Git 拉取指定分支代码
Maven 编译 Java 后端并生成 WAR
Node.js / npm 安装前端依赖并构建 Vue 项目
ZIP 生成统一发布包
SSH / SCP 远程执行部署脚本及上传发布文件
Tomcat 运行 MES Web 应用
Shell 执行远程部署、健康检查和回滚

5.8 第八步：配置立即部署与定时部署

流水线支持两种部署模式。

立即部署： 构建、打包完成后，直接进入上传和部署阶段。

定时部署： 先完成构建与打包，再等待到指定时间执行上传和部署。

这种设计可以将耗时较长的编译操作提前完成，减少计划发布时需要等待的构建时间。

需要注意，定时部署等待期间，Jenkins 任务仍然处于执行状态。因此，应合理选择发布时间，并确认 Jenkins 服务、构建节点和相关网络在等待期间保持可用。

5.10 第十步：停止 Tomcat 并备份当前版本

远程部署脚本先检查目标环境，然后停止 Tomcat。

停止顺序为：

  1. 尝试执行 shutdown.sh。
  2. 等待 Tomcat 正常退出。
  3. 尝试执行 catalina.sh stop 10 -force。
  4. 仍未退出时发送 TERM 信号。
  5. 最后使用 kill -9 作为强制停止手段。

5.12 第十二步：实现失败回滚

部署过程中发生错误时，远程脚本通过错误处理机制尝试执行回滚。

主要流程如下：

  1. 停止当前 Tomcat。
  2. 删除部署失败的新版本目录。
  3. 删除本次上传的 ZIP 文件。
  4. 优先使用 B.F.mes200 作为恢复来源。
  5. 如果正式备份无效，尝试查找历史备份目录。
  6. 将备份复制回 mes200。
  7. 重新启动 Tomcat。
  8. 对恢复后的版本执行完整健康检查。

回滚的目标不仅是恢复文件，还要确认恢复后的应用能够正常启动。

不过，回滚并不是绝对成功的保证。如果备份本身不可用、磁盘空间不足、权限异常或者原版本也存在问题，回滚仍可能失败。因此，生产发布前仍应确保有可用备份，并验证实际恢复流程。

这种顺序可以避免在第一个节点尚未通过检查时，就继续更新第二个节点。

但需要区分两种情况：

  • 单节点回滚： 当前失败节点尝试恢复自己的部署前版本。
  • 双节点整体回滚： 如果 102 已经部署成功，而 101 后续部署失败，当前流程不会自动将 102 恢复到本次流水线执行前的版本。

因此，当前方案具备单节点失败回滚能力，但尚不能视为完整的双节点事务性发布或全局回滚机制。

5.14 第十四步：查看 Jenkins 构建结果

每次流水线执行完成后，可以通过 Jenkins 控制台查看阶段执行日志和最终结果。

当前流水线记录的主要耗时包括：

  • 前后端代码检出。
  • npm 依赖安装或缓存恢复。
  • npm 前端构建。
  • Maven 后端构建。
  • 前后端合并。
  • 发布包生成。
  • 发布包上传。
  • 远程部署。

同时，流水线通过 post 区块记录成功、失败状态，并归档 package/*.zip 发布产物。

排查问题时，应重点区分：

  1. 代码检出失败。
  2. 前端依赖或编译失败。
  3. Maven 编译失败。
  4. 发布包缺失必要文件。
  5. SSH 连接或文件上传失败。
  6. Tomcat 启动或应用健康检查失败。
  7. 自动回滚失败。

这样可以根据失败阶段快速缩小排查范围，而不是只关注最终的 SUCCESS 或 FAILURE 状态。

六、实施成果与收益

6.1 建立统一的自动化交付流程

通过 Jenkins Pipeline，将前后端代码检出、并行构建、环境配置覆盖、发布包生成、文件上传、Tomcat 部署及健康检查统一到一个执行流程中。

减少了人工切换工具和逐步执行命令的需要，也使发布步骤更加标准化。

6.2 提升构建效率

前端和后端采用并行构建，减少了原本必须串行等待的时间。

前端进一步使用 npm 缓存与 node_modules 缓存，在依赖锁文件未发生变化时可以恢复缓存，避免重复安装全部依赖。

实际效率提升幅度需要结合 Jenkins 每次运行记录进行统计，不能仅根据启用了缓存就直接认定具体节省了多少时间。

6.3 降低多环境配置混用风险

通过 config/131、config/102 和 config/101 目录分别管理环境配置，并在发布包生成阶段覆盖对应配置文件。

不同目标环境使用独立的发布包，减少了部署过程中手工调整配置的需求。

6.4 提升生产发布的可控性

通过参数检查、定时部署、严格 SSH 主机密钥校验、部署前检查和阶段日志记录，提升了发布流程的可控性。

生产双节点采用先 102、后 101 的顺序，并要求第一个节点完成部署流程后才进入第二个节点。

6.5 增强故障恢复能力

部署脚本能够在满足回滚条件时，自动停止 Tomcat、恢复备份目录并重新启动服务。

回滚后继续执行健康检查，有助于判断旧版本是否恢复到可运行状态。

同时，历史备份目录为后续问题追溯和版本恢复提供了额外依据。

6.6 为后续持续交付优化奠定基础

当前流程已经具备自动构建、环境专用打包、部署检查和单节点回滚等能力。

后续可以继续完善以下内容：

  1. 增加自动化测试及代码质量检查。
  2. 严格定义登录接口的健康检查标准。
  3. 建立生产双节点全局回滚机制。
  4. 增加发布前人工审批和生产发布权限控制。
  5. 对构建耗时、部署成功率和回滚次数进行统计。
  6. 优化备份保留策略，避免历史目录持续增长。
  7. 增加发布通知和异常告警。

七、总结

本项目以制造企业 MES 系统为实践场景，基于 Jenkins Pipeline，将原本分散的构建、打包、上传和部署操作整合为统一的自动化交付流程。

通过前后端并行构建、npm 依赖缓存、环境配置隔离、定时发布、生产双节点顺序部署、健康检查和失败回滚，提升了软件发布过程的标准化程度与可追踪性。

需要认识到，自动化部署并不意味着生产发布不存在风险。只有将自动化构建、质量验证、部署监控、备份恢复和发布治理结合起来，才能逐步形成稳定、可靠、可持续优化的制造企业 DevOps 交付体系。
