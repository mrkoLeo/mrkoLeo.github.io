从 SVN 到 Gitea：制造业内部 Git 服务搭建与规范化落地实践

发表于 2025-11-21 分类于 03-工具 ， 01-Git 阅读次数： 本文字数： 1.8k 阅读时长 ≈ 7 分钟

记录了企业内部代码管理平台从 SVN 向 Git 化演进的实践过程。由于公司内部长期使用 SVN 进行代码管理，在多人协作、权限管理、分支开发及代码追溯等方面逐渐暴露出问题。结合团队规模较小、运维资源有限等实际情况，最终选型轻量级 Git 服务平台 Gitea，并基于 Linux RHEL8 虚拟机完成内部 Git 服务部署。

文章详细介绍了虚拟机申请、Gitea 安装、MariaDB 配置、SSH 免密登录、多仓库管理、组织权限规范等完整流程，同时整理了日常运维命令与常见问题排查经验，适合作为制造业中小团队内部 Git 服务落地参考方案。

背景

随着 MES、ERP、OA、报表平台等系统逐渐增多，公司内部开发脚本、自动化工具以及业务系统代码量持续增长。

当前公司仍以 SVN 作为主要代码管理工具，虽然能够满足最基础的代码存储需求，但随着开发人员增加，逐渐出现以下问题：

  • 多人协作效率低
  • 分支开发困难
  • 权限管理不灵活
  • 无法规范代码评审流程
  • 自动化集成能力弱
  • 新项目初始化成本高

尤其在制造业环境中，MES、ERP、设备接口、自动化脚本等项目往往由多个开发人员共同维护，SVN 已经难以满足后续持续扩展需求。

因此，决定在公司内部搭建统一 Git 服务平台。

遇到问题

SVN 已无法满足当前开发模式

当前环境主要存在以下问题：

  • 所有项目共用 SVN 仓库
  • 权限粒度较粗
  • 无法方便进行 Feature 分支开发
  • 多人同时修改容易冲突
  • 无法规范 Commit 历史
  • 缺少组织化管理能力
  • 缺少统一代码平台

例如：

  • MES 系统项目
  • ERP 接口项目
  • 公司内部SpringBoot系统

均散落在不同 SVN 路径中。

后期维护成本越来越高。

痛点

1. SVN 不适合多人协作开发

SVN 更偏向集中式版本管理。

开发人员修改代码前需要先更新，提交时容易发生冲突。

尤其多人同时开发：

  • MES接口
  • 数据同步
  • 自动化脚本

时，经常互相覆盖代码。

2. 缺少规范化组织管理

不同系统项目：

  • MES
  • ERP
  • OA
  • 公司内部SpringBoot系统

均没有统一归属。

导致：

  • 仓库命名混乱
  • 权限难管理
  • 无法快速定位项目

3. 无法支持现代 DevOps 流程

后期计划逐渐引入：

  • 自动部署
  • CI/CD
  • 自动化测试
  • Git Hook
  • Jenkins

SVN 对这些支持较弱。

4. 运维成本增加

SVN 权限配置复杂。

新增员工：

  • 创建账号
  • 分配目录权限
  • 调整访问策略

均需要人工处理。

问题分析

为什么选择 Git

Git 属于分布式版本控制。

相比 SVN：

对比项 SVN Git
架构 集中式 分布式
分支管理 较弱 非常强
离线提交 不支持 支持
协作能力 一般 强
DevOps支持 较弱 强
社区生态 一般 非常丰富

Git 已经成为当前主流代码管理方案。

为什么选择 Gitea

虽然 GitLab 功能更强，但结合公司现状：

  • 开发人数少
  • 项目规模中等
  • 运维资源有限

最终选择轻量级 Gitea。

Gitea 具有以下优势：

特性 Gitea
资源占用低 √
部署简单 √
中文友好 √
支持组织管理 √
支持SSH √
支持权限控制 √
支持Webhook √

非常适合中小型制造业团队。
